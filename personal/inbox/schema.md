# Personal Inbox 写作与维护契约

`inbox.md` 是 Personal Inbox 个人关注内容的事实源，可以直接阅读和版本控制。本机 Web App 与 `bin/work` 使用同一套维护逻辑，不生成第二份内容库。

Inbox 只回答两件事：现在是否需要用户处理什么，以及其他少量承诺目前处于什么状态。它不是项目看板，不复制 Work 文档、Issue、task 正文或短命执行记录。项目事实和实施仍由 owning task 或项目主线程维护。

## 四个固定状态

按顺序保留四个二级章节：

| 页面分类 | 用户语义 | Markdown 章节 | 使用条件 |
| --- | --- | --- | --- |
| 需要我 | blocked | `Needs you` | 当前确实需要用户作决定、提供输入或操作，才能解除阻塞；写清问题与推荐。 |
| 进行中 | in progress | `In progress` | 已承担并正在推进的工作；包括负责人仍在跟进、不需用户处理的外部依赖，摘要说明等什么及下一步。 |
| 等待中 | backlog | `Waiting` | 保留但暂不推进的想法、待排事项或主动暂停项；不是泛指所有外部等待。 |
| 已完成 | completed / archived | `Done` | 已交付完成，或已取消、结束归档且无继续推进安排；摘要明确是哪一种，归档不等于实现或验收成功。 |

四个 Markdown 章节名与顺序保持不变，它们是现有解析格式，不要求与用户语义的英文名称相同。可恢复但暂时搁置的工作放 backlog；明确结束的工作放 archived。只因负责人尚未排期，不能标成 blocked 要用户催办。负责人可解决的技术问题由负责人承接；确需用户输入时才进“需要我”。

章节位置表达个人关注状态；共享工作的生命周期由工作工具单独记录，不因移动个人分类而自动完成、暂停或取消。非 `Done` 使用 `[ ]`，`Done` 只使用小写 `[x]`。空章节只写 `_暂无事项。_`，不能与条目混用；不能为了让 Inbox 看起来有内容而虚构 `Needs you`。

## Canonical 单行 grammar

```markdown
- [ ] 确认发布范围 — 下一步：选择本次发布平台。 · [Issue](https://example.com/issues/1) · [Work](../../agent-data/projects/workspace/work/active/release-scope.md) <!-- work:0123456789abcdef0123456789abcdef -->
```

- 标题和摘要都不可为空，只使用唯一分隔符 ` — `，整项保持一行。
- 尾部关联都可省略；`Issue` 与 `Work` 各至多一次，顺序固定为 Issue → Work。
- Issue 只接受不含用户名或密码的完整 `https://` URL；它是只读入口，应用不抓取或写回远端状态。
- Work 从 `personal/inbox/` 写为相对路径，解析后限于 `agent-data/projects/**/work/active|archive/*.md`。新增关联应选当前存在的普通 Markdown 文件；读取旧 Inbox 时允许格式合法但目标已缺失的关联，以保持其他事项可读，这不表示关联仍有效。通过应用保存时，提交内容中的 Work 关联均须当前有效，失效关联需先修正或移除。
- 标题按大小写和空白归一后全局唯一。
- 行尾可有至多一个 `<!-- work:32位小写十六进制 -->` 隐藏标记，由工具维护，用于在改名、移动和归档后识别同一事项。旧条目没有标记时仍兼容读取；人和 Agent 不需要手工编辑或复制它。
- 不增加 frontmatter、表格、子列表或其他机器字段。

## 摘要的阅读约定

摘要默认只写简短当前进展与下一步；待决定项写问题和推荐，完成项写结果。准确提交、测试数量与 Review 过程留在关联 Work，影响用户判断的未完成、风险和可用性边界仍须说清。Work 的目标、方案、阶段与证据层次遵循[共同上下文](../../practices/collaboration/context.md#先读懂当前工作再按需取得细节)，Inbox 的判断和同步遵循[关注视图](../../practices/collaboration/chief/inbox.md)。本约定不增加字段或改变解析格式。

## 怎样维护

记录、启动、改名、暂停、恢复、交接、个人安排与收尾优先使用 workspace 根目录的 `bin/work`，用法见 [Work 日常维护](../../practices/collaboration/workflow.md)。查看和编辑个人关注内容也可启动本机应用：

```text
python practices/communication/html/inbox/scripts/inbox_app.py --repo-root /path/to/workspace
```

应用默认只绑定 `127.0.0.1:8765`；端口占用时用 `--port <n>`。GUI 支持新增、编辑、改状态、Issue 关联和 Work 选择，并用 revision 检查防止编辑期间的外部变更被覆盖。看到 stale 错误时，当前表单草稿会保留；重新加载最新 Inbox 后人工核对，不自动合并。

也可以直接编辑 Markdown。来源状态、下一步或用户责任变化时，更新一行摘要并把整行移到正确章节；完成后只保留仍有价值的结果入口；最后一项删除后恢复空标记。应用读取时会拒绝不符合 grammar 的整份文件，不会忽略未知内容后保存。

## 置顶与顺序

每个区块内按手动顺序显示，不按事项标题排序。置顶是持续状态，条目在身份注释前使用可选的 `<!-- pinned -->` 标记；未置顶不写标记。置顶事项稳定排在该区块普通事项之前，组内顺序仍可调整。API 的可选 `pinned` 字段只接受布尔值；旧客户端省略时保留已有状态。移动区块、编辑或 Work 更新不清除置顶状态。

界面的“上移”是一次移到当前置顶组或普通组最前面，不改变置顶状态；拖动只改变顺序或个人分类，不改变工作生命周期。
