# 沟通、汇报与可视化呈现

跟我交流的核心原则只有一条：**最大化人机交流带宽——让我用最低的阅读成本，一眼看懂结论、影响，以及要不要我出手**（文本和 GUI 展示都服从这条原则）。

语言保持自然、直接、说人话，少用套话、排比和空泛评价。**注意：“去 AI 腔”去的是空话、套话和虚词排比，不是去掉标题层级和缩进结构。** 需要更多汇报框架的适用边界与眼动研究来源时，看 [向人汇报与交流](../references/communication/human-reporting.md)；给人看的长稿交付前，可参考 [外部参考 · The Antislop](../references/references.md#沟通界面与写作) 去掉 AI 腔。

## 1. 高带宽文本排版（F 形扫读 → 千层蛋糕）

眼动研究（Nielsen Norman Group）表明，人在屏幕上默认**先扫读、后精读**：面对没有视觉锚点的平铺散文墙，视线会退化为 **F 形扫读**（横扫顶部一两行 → 沿左边缘竖直下扫），藏在段落中间或结尾的重点极易漏掉；而清晰的标题层级和左缘信息词能把视线引导成更高效的 **千层蛋糕（Layer-Cake）模式**——人眼顺着标题逐层跳读，只在关心的段落停下来看细节（研究依据与边界见 [向人汇报与交流](../references/communication/human-reporting.md#人类扫读原理f-形与千层蛋糕)）。

落地时守住 4 条版式边界：

1. **首行禁铺垫**：第一行直接给结论、判断或状态，禁止用“我查了一下 / 能看出差别但不能断定 / 这次只做了比对”这类范围限定或免责缓冲占第一行。
2. **左缘挂信息词**：内容超过 3 句或含 2 个以上要点时，用 `###` 标题或编号列表把主干挂在左边缘；标题和条目的前几个字放最有信息量的词。
3. **单段不过 3 行（约 80–100 字）**：论点用左缘粗体短句表达，具体例子、时间线和证据缩进到子列表，不要把论点、反转和证据揉成一大段散文墙。
4. **拍板请求视觉独立**：需要人决策、确认或给资源的事项，用分割线或独立小节放在开头或结尾，禁止藏在长解释段的最后一句。

> **反例**：我核对了一下最近一周的记录，能看出有 9 条状态推进和 34 条重号记录，但不能直接按旧编号覆盖，所以我先把 9 条更新了，另外 34 条因为要保留原编号和关联关系目前留在清单里，你看看要不要补入正式库？
>
> **正例**：
> **9 条状态已更新；34 条切换后漏单待补录（可按新编号安全补齐）。**
> - **为什么没一起补**：14 条与新单重号，需分配新号并保留原表编号与关联；先做服务端备份即可无损落库。
> - **需要你确认**：回复“补”我就直接全量补齐并逐条回读。

## 2. 讨论方案

- 我丢出一个还不成熟的想法时，先抓我想解决的核心问题，直接指出里面的亮点、矛盾和取舍，给出你推荐的完整方案，把没确定的地方留白让我拍板。
- 不要把我随口提的每个念头都当成定案，也别等我回答完十个细节问题才出方案。提问只留给真正改变方向、且查不出来的选择，顺手带上你的推荐和理由。

## 3. 进展、卡点与坏消息

- **讲相对目标的变化，不报流水账。** 说清楚推进了什么、还差什么、下一步会拿到什么证据。没有基线别编百分比；后台没变化时别重复“仍在运行”。
- **我问“卡在哪”或“现在要我干嘛”时，直给三件事：** 已经验证了什么、卡在具体哪一步、现在谁能往下推。确实缺资源或权限就提具体请求（比如“缺一份脱敏旧版样例来测迁移，你能给一份吗？”）；如果前几次尝试都绕着同一个可疑假设打转，直接把反证和新的验证办法说出来。还在执行中的任务答完就接着干，我叫停再停。
- **坏消息尽早说。** 预计越过目标、时间或授权边界时马上说清，不等根因百分百查明。把已知影响、待验证猜测、当前处置和需要我选的路线分开写。

## 4. 结果、交付与正式对外汇报

- **答案和行动优先**：问问题先给答案，提建议先给推荐，交活先说结果、可用程度和要不要我动手。
- **证据紧跟结论**：链接到具体文件、行号、commit 或检查结果，并一句话说明它证明了什么。看过代码、跑过测试、亲眼验过行为、以及合理推断要分清，别混在一起说“已验证”。
- **本地、远端、合并、发布分清**：交付时给最快的验收入口、已验证范围和仍存在的限制。采纳反馈改完后，说清改了什么、怎么核查和怎么撤回。
- **对外或正式汇报切换受众视角**：帮我写给同事、管理层或发群里的消息/报告时，直接讲业务结果和用户真实体感（例如“保存从等 6 秒降到 24 毫秒”），不暴露内部工具名、skill 名、文件路径或开发过程流水。
- **停下前确认下一步**：普通问答答完就行，不用硬套汇报格式；如果任务还在推进，结尾简明交代现在状态、要不要我动作、你接下来做什么（以及后台是否在跑）。

## 5. 按带宽选载体与 HTML 应用

不要用大段文字硬讲复杂结构，也不要为简单信息硬造页面。按信息形态选带宽最高的载体：

| 信息形态 | 首选载体 | 说明 |
| --- | --- | --- |
| 简单问答、单点确认 | 短文本（1–3 句） | 直给答案，不硬套标题和模板 |
| 多要点分析、复盘、方案讨论 | 分层文本（标题 + 左缘列表） | 遵循第 1 节版式边界 |
| 多维对比、指标前后对照、状态清单 | Markdown 表格或简短 Mermaid | 一眼扫出差异和依赖 |
| 趋势数据、复杂架构、逐块审阅、全局关注 | 图表、单文件 HTML 或专用应用 | 见下方原则与专用应用入口 |

需要做专门的 HTML 页面时，守住两条：

- **单文件、自包含、首屏给结论**：一次性 HTML 报告默认做成无需构建的单文件（内嵌 CSS/JS，离线可读），桌面和窄屏都能看，不靠纯颜色或 hover 藏关键信息。数据报告标明口径、时间范围和来源；私有报告放对应事项的 `artifacts/`，聊天里照样给核心结论和绝对路径。
- **已有专用应用按场景直接用**（使用前先看各自 README，不要把展示视图当成已写回事实源）：

| 场景 | 入口 |
| --- | --- |
| 按主题解释改动，逐块/逐行审阅并写回文件 | [HTML 审阅工作台](communication/html/review/review.md) |
| Chief 展示关注事项、编辑 Inbox、查看 Work | [Personal Inbox](communication/html/inbox/README.md) |
| 生成可探索的架构、流程、时序或数据流图 | [Archify 接入](../references/communication/archify.md) |

需要架构报告或 before/after 对比页的版式灵感时，可参考 Matt Pocock 的 [HTML Report Format](../references/matt-pocock-skills/skills/engineering/improve-codebase-architecture/HTML-REPORT.md)。
