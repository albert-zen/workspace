# 独立 Review

Review 的目标是用独立视角找反例：这份改动有没有真正解决用户原本想解决的问题？证据撑不撑得住结论？有没有破坏边界、埋下回归或引入多余复杂度？

## 1. 什么时候安排独立 Review

按改动影响决定，不搞一刀切：
- **小范围、低风险、一眼能核对的改动**（例如小文案调整、简单笔记、局部机械修改）：负责人自己检查即可，不必另开 Reviewer。
- **高影响或复杂改动**（核心逻辑、架构边界、权限与数据安全、协作契约、工作空间关键读取路径，或我明确要求审阅时）：安排干净上下文的独立 Reviewer。如果当前环境没有独立 Agent 能力，由负责人自查并如实注明未做独立 Review。

## 2. 核对“原始意图”，不只看代码惯例

Review 不能只对照通用编码规范挑毛病，更要对照**这项需求、修复或重构的原始意图**——很多看起来“代码很工整”的改动，其实悄悄偏离了我原本想要的东西。

- **原始意图从哪来：**
  1. 派发者在启动 Reviewer 时，应直接把原始需求、关键约束和相关决定放进派发说明（最好附关键原话或准确摘要），并给出固定审阅对象（精确 commit / PR / 文件版本，不要审正在变动的工作树）。
  2. 如果任务有对应 Work、PR 或 Issue，Reviewer 优先读 Work 的 `## 事项说明`、关联的 `intent.md`（可用 `work intent show` 或沿 `work resume` 提示读取）以及 PR/Issue 原文。
- **如果意图不清怎么办：** 不要因为部分细节没写死就卡死整个 Review 流程。按现有代码、文档和上下文做**保守推断**继续完成审阅，并在结果里明确单列两部分：① 本轮 Review 基于哪些**意图假设**做的判断，② 哪些**设计意图差异或模糊点**值得在交付时向我确认。不要把个人风格偏好包装成“必须修改”的产品需求。

## 3. 怎么写 Finding 和裁决

- **可裁决、有证据**：每条 finding 写清位置或行为、违背了哪条意图或约束、触发条件、实际影响和证据。把“已复现的缺陷”“从代码推断的风险”和“可选建议”分开标明。
- **Reviewer 默认只读**：除非明确授权，不直接改受审代码；也不要因为顶着 Reviewer 角色就要求重跑无关检查或顺手扩需求。
- **负责人裁决，不盲从**：负责人读完报告后按需求与证据决定采纳哪些 finding；拒绝阻塞项时留下理由。执行者修完后给出证明原问题已解决的新证据，旧版本的通过结论不自动覆盖新版本。

## 4. 最多三轮收敛（当前默认策略）

三轮上限用来控成本，可以由我按任务调整，不要求跑满：

- 每次针对一个固定版本算一轮，新一轮用新的独立 Reviewer；修 bug 或换执行者不重置计数。
- 前两轮有采纳的阻塞问题就修复再审；没有未解决阻塞项且必要检查通过，就进入集成或交付。
- 第三轮后若仍有采纳的阻塞问题，由负责人拍板一次最终修复并验证，不再开第四轮，交付时如实注明“最终修复后未再独立 Review”。如果还是达不到要求，把缺口和可选路径交给我，不要把未完成写成通过。
- 如果连续几轮 Review 都在暴露同一类含糊目标、脆弱边界或烂测试，停下来回到方案和环境（[园丁原则](../garden.md)）修根因，不要指望多审几轮解决问题。

> 交付前的最终判断由负责人承担：CI 绿了或 Reviewer PASS 都只是证据之一，不代替负责人确认整体结果符合意图，也不代替用户验收。
