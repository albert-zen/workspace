# 工程设计与验证

这份文档是 [园丁原则](../garden.md) 落到单次开发任务时的具体做法：怎么选设计边界、怎么用行为测试和真实验证兜底。

## 1. 设计判断

- **先沿真实入口理解问题。** 从用户或调用方能观察到的行为出发，读真实代码、测试、项目文档和当前设计意图，不要靠猜模块名字做设计。
- **比较有实质差别的方案。** 关注它们各自引入多少新概念、调用方需要多懂多少细节、改动波及面多大、反馈快不快。“最小方案”指的是概念和影响面小，不是补丁行数少。
- **用 Deep Module 承担真实复杂度。** 好的模块对外提供少量清晰接口，把校验、持久化、重试、冲突处理这些脏活藏在里面；少写那种只做透传、却逼着调用方懂全部内部细节的薄包装层。接口要诚实——失败和冲突直接返回可处理的结果，别藏进日志或返回含糊的成功。
- **抽象来自真实共同变化。** 两段代码长得像可以先各自局部呆着；等重复确实造成同类 bug 或同步修改痛苦时，再提炼边界。
- **不确定边界先切纵向切片。** 比如做保存功能，先打通写入、重读和并发冲突这一条细切片，再去铺完整界面，别等全部写完才发现最底层假设错了。
- **让代价配得上需求。** 新增状态机、权限层、框架或外部依赖时，必须对应当前真实需求；同时保持改动聚焦，不顺手大重构无关代码，不把个人偏好私自升级成产品功能。

需要深入判断模块深度、seam 和重构手法时，按需查阅 [外部参考 · Matt Pocock Skills](../references/references.md#matt-pocock-skills本地-submodule) 里的 `Codebase Design` 与 `Improve Codebase Architecture`。

### 界面改动

- 先从项目现有页面、组件和用户操作出发，想清楚哪些信息必须同屏、哪些按需展开；沿用已有设计系统的小改动直接遵循项目约定即可。
- 新做或大改视觉方向时，可参考 [外部参考 · Anthropic Frontend Design](../references/references.md#沟通界面与写作)。涉及交互或布局变化时，用真实浏览器检查窄屏、键盘/焦点和核心交互，交付 PR 时附改动前后同条件对比截图。

## 2. 行为导向 TDD 与验证

验证不是写完代码再补的收尾步骤，而是从动手前就开始设计：什么证据能明确区分“问题还在”和“已经修好”？改动最可能弄坏哪里？

- **行为变更与修 bug 默认用 TDD。** 先针对一个有实际意义的行为写失败测试，确认失败确实来自目标问题，再实现让它通过，最后在测试保护下整理结构。按行为一个个推进，不要一次性臆造一整套接口测试再大批量实现。具体做法和排错方法可参考 [外部参考 · Matt Pocock Skills](../references/references.md#matt-pocock-skills本地-submodule) 里的 `Test-Driven Development` 与 `Diagnosing Bugs`。
- **测行为，不绑死内部实现。** 通过模块公开接口观察结果；只对外部服务、时钟或平台边界做必要隔离，不要把整段业务逻辑都 mock 掉。测试失败应该能说明“哪个用户行为坏了”，内部重构不该让一堆无关测试跟着挂。
- **删改旧测试前先查它保护了什么。** 遇到只断言私有方法或源码形状的脆弱测试，先查清楚它原本要防哪个回归，用行为测试接住以后再清理旧断言。
- **难以先写单测时用等价反馈。** 比如用复现脚本、探针或真实操作建立快速反馈，说明原因及后续能否自动化。纯文档、文案或机械改动用对应检查即可，别为了形式造无意义的测试。
- **盯住真实风险，不拿弱检查冒充强证据。**
  - 持久化：测写入、重读和并发冲突；
  - 界面：看真实交互、窄屏和关键可访问性；
  - 删除或外部副作用：核对真实作用对象；
  - 类型检查、lint 和构建只能证明它们覆盖的那一层，不能代替运行时行为验证。需要更多交付证据思路时，参考 [外部参考 · pstack Verify and Ship 与 tstack Proof](../references/references.md)。
- **结论绑定精确对象。** 写清验证针对的是哪次提交或哪份产物；代码继续改了，就判断哪些旧验证失效并补验受影响部分。环境缺项或已有基线失败如实区分——既不把平台噪声赖到新改动头上，也不拿“本来就坏着”掩盖新引入的错误。

达到既定验收条件、按 [独立 Review](review.md) 处理完接受的审阅问题、文档和代码一致，就进入交付，不要没有新风险还无限加检查。
